# AlphaServer DS25 work packet

The second Titan board ([titan.md](titan.md)), after the ES45
([es45.md](es45.md)).

**Branch**: `platform/titan-ds25` · **Config**: `platform = "ds25";`
· **Status**: L5 (its update utility installs SRM V7.3-2 into the flash; the
console boots from the flash; network boot; OpenVMS 8.4 boots its CD and an
installed disk to login on one and two processors, NIC interrupts checked on
all four hoses); L3 structural against a real DS25's listing (owner's guide)

## Firmware

`roms/alpha-firmware-v7.3/DS25/DS25_V7_3.EXE`, the update utility, raw
(`FW_RAW_IMAGE`), the same form as the ES45's. Its console reports "OpenVMS
PALcode V1.98-43" and runs up to 0x668000 in memory (`console_bytes`
0x680000). It installs three images:

```
FSB             Updating to V7.3-3...  Verifying V7.3-3...  PASSED.
SRM             Updating to V7.3-2...  Verifying V7.3-2...  PASSED.
srom            Updating to V1.4-G...  Verifying V1.4-G...  PASSED.
```

(`lab/platforms/ds25/lfu-update-console.log`; the flash it leaves is
`lab/platforms/ds25/flash-v73.rom`.) Booted from that flash with no image:

```
AlphaServer DS25 Console V7.3-2, built on Feb 27 2007 at 13:10:18
P00>>>
```

(`lab/platforms/ds25/l2-srm-console.log`.) The installed console decompresses
to below 0x224000 ("memory low limit").

## Network boot (L4)

A DE500 at hose 0 slot 8 on the UDP backend, `net_peer.py` answering:
`boot ewa0 -protocols bootp` gets its BOOTP reply, reads `boot.img` over
TFTP (65 blocks, 65636 bytes) and runs it to its HALT
(`lab/platforms/ds25/evidence/l4-net-*.log`).

## OpenVMS 8.4 (L5)

From `lab/platforms/ds25/` (scripts `run.sh`, `srm.sh`, `nic_check.sh`;
evidence in `evidence/`):

- the CD (`lab/ALPHA084.ISO` as dqa1) to the date prompt and the install
  menu, on one and on two processors (`l5-cd-*cpu-console.log`);
- the disk installed on the ES40 (`lab/vms84/disk-installed.img`, cloned)
  to the SYSTEM login: `HW_NAME` "AlphaServer DS25", SYSTYPE 38, CPUTYPE 8;
  one processor (`ACTIVECPU_CNT=1`, `l5-disk-1cpu-console.log`) and two
  (`Active 0,1`, `l5-disk-2cpu-console.log`). The first two-processor boot
  bugchecked during startup (SSRVEXCEPT in the CLUE$SDA process,
  `l5-disk-2cpu-run1-bugcheck.log`); later two-processor boots (one more
  disk boot and two NIC checks) all reached login. **[open: one failure in
  four two-processor runs; the JIT's two-processor runs of the Tsunami
  boards have intermittent failures of their own (alpha-models roadmap)]**
- DE500s at hose 0 slots 9 and 10, hose 1 slot 2, hose 2 slot 5 and hose 3
  slot 1 each counted 127-128 broadcast frames in LANCP in 40 s with one
  processor (`nic_check.sh`, `l5-nic-nic3-console.log`) and with two
  (`l5-nic-nic4-console.log`): the interrupt map is right on every hose. In
  one other two-processor run two of the five counted 34 and 25
  (`l5-nic-nic2-console.log`) **[not reproduced; the ES45 with two
  processors and the same check counted 127-128 on all five]**. (The first
  check, `l5-nic-nic1`, used hose 0 slot 11, which the board now refuses.)
- The AIC-7899's two channels appear as PKA0 and PKB0, **offline** with one
  error each: OpenVMS has a driver for them, and the inert chip fails its
  initialisation without harm.

## Findings

**First run:** the update utility's console started, probed the four hoses,
started its drivers, and then took an access violation at 0x805.0000.0000
in its powerup process. Its call frames name it: `aicrom_init` ->
`init_aic_flash_rom` -> `aic_rb` -> `inmeml`. `aicrom_init` (0x14a560 in
the utility) does not look for the device: it addresses hose 2 device 1
directly, reads the expansion-ROM BAR (0x30), enables it, and sends AMD
autoselect commands (0xaa to 0x553, 0x55 to 0x2a8, 0x90 to 0x553) to the
flash behind it. With nothing there the BAR read as all ones, and the base
it computed from that ran off the end of hose 2's memory space.

**The device is the on-board Adaptec AIC-7899.** The console's PCI ID table
(0x1745c4/0x1745e0) names 9005:00c0 and 9005:00cf "Adaptec AIC-7899"
(driver `aic78xx`, devices `pk`), and the update utility carries
`aic7899_seeprom_update` and the `aicrom` flash driver. The board builds
`CDs25Aic7899` (`platforms/ds25/`): the two functions' configuration space
(9005:00cf, SCSI class, I/O BAR0 256 bytes, memory BAR1 4 KB, a 64 KB
expansion ROM **[size assumed]**), registers that read 0, and a flash that
reads as erased. No SCSI is modelled. With it:

- `aicrom_init` finds no flash part it knows and returns "00000001 exit
  status for aicrom_init"; the utility goes on to its dialog. A sym53c875
  placed there instead (an experiment) gave the same, so any expansion ROM
  at that place satisfies the utility.
- the console's own `aic78xx` driver initialises "pka pkb" and lists the
  two channels as `pka0.0.0.1.2` and `pkb0.0.0.101.2`; it does not hang on
  the inert registers.

Add-in devices are refused at hose 2 device 1, at the hot-plug
controllers' places and at hose 0 device 11 (in the console's table, but no
physical slot in the owner's guide).

**The interrupt map is the console's table**, at 0x179f10 in the update
utility (one word per slot, a byte per pin, the ES45's layout), and it is
what the console writes into cards' configuration space (DE500s in every
place, `lab/platforms/ds25/l3-slots-intlines.txt`):

| hose | slot: INTA (DRIR bit) |
| --- | --- |
| 0 | 8: 0x14, 9: 0x18, 10: 0x0c, 11: 0x10, 12: 0x0b (one pin) |
| 1 | 1: 0x1c, 2: 0x20, 6: 0x0a (one pin) |
| 2 | 1: 0x00 (the AIC-7899: function 0 INTA 0x00, function 1 INTB 0x01), 5: 0x04 |
| 3 | 1: 0x24, 2: 0x28, 6: 0x09 (one pin) |

Hoses 0, 1 and 3 are the ES45's; hose 2 differs (the ES45 has slot 2 at
0x04 and slot 5 at 0x2c).

**RMC command 9** is sent as on the ES45, and is accepted the same way (a
value chosen to get past "RMC command failure").

**Processor 1's presence (DPR 0xaf).** With one processor the console
read processor 1's FRU image (DPR 0x2200), put a processor 1 node in the
configuration tree with no type in it, and OpenVMS stopped it with
"%SMP-F-CPUBAD, CPU #1 cpu type does not match that of primary" (the HWRPB
slot was empty; the ES45 console, with the same DPR, makes no such node).
The DPR byte 0xaf -- which FRU EEPROMs the RMC failed to read -- is read just
before; the ES40's encoding sets bits 1-3 for absent processors 1-3.
Setting each bit of it in turn with one processor, only bit 7 stopped the
console reading 0x2200 (`lab/platforms/ds25/dpr_bits.sh`). `CDs25Dpr` sets
0xaf to 0x80 with one processor and 0 with two **[bit 7 = processor 1, by
experiment; what bits 0-6 mean on the DS25 is not known]**.

**The SROM version** in the DPR (0x3000) is set to "V1.4-G", the DS25's,
in place of the ES40's "V2.22G" **[spelling assumed]**.

Other unclaimed accesses: TIG offset 0x0c0 (psir, the power-supply
register in the ES40's TIG naming) read 7 times; 16-bit reads across PCI 0
memory 0xc0000-0xdffff (the console looking for a VGA option ROM).

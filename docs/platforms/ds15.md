The third Titan board ([titan.md](titan.md)), after the ES45
([es45.md](es45.md)) and the DS25 ([ds25.md](ds25.md)).

**Branch**: `platform/titan-ds25` · **Config**: `platform = "ds15";`
· **Status**: L5 (its update utility installs SRM V7.3-2 and SROM V1.0-1 into

## Firmware

`roms/alpha-firmware-v7.3/DS15/DS15_V7_3.EXE`, the update utility, raw
(`FW_RAW_IMAGE`). Its console reports "OpenVMS PALcode V1.98-7" and runs up
to 0x702000 in memory (the row's `console_bytes` is 0x710000, what the
decompressed-image cache keeps). It updates three devices:

```
SRM             Updating to V7.3-2...  Verifying V7.3-2...  PASSED.
rt              Updating to V1.2-0... RMC error status 81 ... FAILED.
srom            Updating to V1.0-1...  Verifying V1.0-1...  PASSED.
```

`rt` is the RMC's own firmware, sent with RMC command 0xf0, which is not
modelled (`lab/platforms/ds15/lfu-update-console.log`; the flash it leaves:
`lab/platforms/ds15/flash-v73.rom`). Booted from that flash:

```
AlphaServer DS15 Console V7.3-2, built on Feb 27 2007 at 13:07:33
>>>
```

(`lab/platforms/ds15/l2-srm-console.log`). A one-processor console's prompt
is `>>>`.

## Sources

- The update utility and the installed console. Both carry a symbol table
  (pairs of 32-bit procedure descriptor and name, as the DS10's does): in
  the utility's memory at 0x1721b0 (4007 names), in the installed console
  at 0x150b30. A procedure descriptor's entry point is the quadword at +8,
  and `pv` holds the descriptor, so a routine's linkage is reached as
  descriptor + offset. Memory images: `lab/platforms/ds15/ds15-v73-lfu.rom`
  (the utility, 16-byte header) and `ds15-v73-mem.bin` (the installed
  console's memory, from address 0).
- The routines above were found with `ALPHABOX_TRACE_CALLS`, DPR access
  traces and a watch on reads of a message string's address (temporary
  hooks in `CDPR` and the interpreter's load path, not committed), and
  named from the symbol table.
- *hp AlphaServer/AlphaStation DS15 Owner's Guide* EK-DS150-OG.A01
  (`lab/docs-titan/ds15_owners_guide.pdf` and `.txt`).

## Findings

**The RMC is reached differently.** The DS15 console reads the ES40's
dual-port RAM for the processor's power-up status (0x00-0x1f), the
environment block (0x80-0xff) and FRU images, but:

- its RMC command mailbox is at **0xb00**, not 0xf9: size 0xb00, qualifier
  0xb02-0xb03, completion code 0xb04, response id 0xb05, command 0xb06,
  command id 0xb07, data from 0xb10 (`issue_rmc_cmd` 0x9ccc0 and the wait at
  0x9cde0 in the utility). The ES40's layout answered nothing there and the
  console printed "RMC timed out waiting to complete - command 2".
  `CDs15Dpr` completes commands 1, 2, 3 and 9 with code 0 and answers
  others with 0x81 **[accepted without effect: values chosen to get past
  "RMC command failure"]**;
- `report_rmc_errors` (0x91960) reads DPR 0xb8-0xff with other meanings
  than the ES40's: 0xb9 nonzero is "RMC detected: DPR Test Failure", 0xba
  bits 0-2 are fault LEDs (the ES40's 0xba = 0xba lit "Over-Temperature"),
  0xca nonzero lists errors, and 0xdb must be 0xdb or the console reports
  "RMC detected: TIG Status Failure". `CDs15Dpr` sets them so;
- the same routine reads the TIG's psir (offset 0x0c0) and prints "RMC is
  not Ready" unless bit 7 is set. `CDs15Tig` answers psir with 0x80 **[the
  other bits not known]**.

**The halt register does not halt the DS15's processor.** The console's
PALcode writes 0xf to TIG offset 0x5c0 (`ev6_halt` in the ES40's naming) at
reset, and nothing clears it; the ES45 and DS25 consoles clear the
primary's bit once it has won arbitration. With the ES40's meaning the one
processor took a halt interrupt without end (IRQ statistics: 16 million
interrupts in 5 s, EI4 always set), its interval timer was never serviced,
and the console printed "CPU 0 speed is 357 MHz" (`krn$_timer_set_cycle_time`
gave up waiting for ticks) and "*** no timer interrupts on CPU 0 ***".
`CDs15Tig` keeps what is written there and drives nothing **[assumed: what
the register does on a DS15 is not known; a TIG of a different kind is
consistent with FWREADME listing no TIG firmware for the DS15 and with the
real DS15's "TIG Rev 1.9" against the ES45's and DS25's 2.6]**.

**The interrupt map is the console's `pci_irq_table`** (0x1647c8 in the
utility), read by `map_irq` (0x967c0): from device 7 on each hose, a byte
per pin, 16 bytes per hose; hose 0 device 13 gets 0xee (ISA) before the
table is read. The lines the console writes into DE500s placed everywhere
agree (`lab/platforms/ds15/l3-slots-intlines.txt`):

| hose | device: INTA.. (DRIR bit) |
| --- | --- |
| 0 | 8: 0x0d, 0x0c; 9: 0x1c; 10: 0x04; 13: 0xee (IDE) |
| 2 | 7: 0x28-0x2b; 8: 0x24-0x27; 9: 0x18-0x1b; 10: 0x14-0x17 |

**The AIC-7899 may be absent.** The update utility's `aicrom_init` addresses
hose 0 device 8's expansion ROM as the DS25's does at hose 2 device 1, but
with nothing there the base it computes stays inside hose 0's memory space,
the flash probe finds no part and returns 1 ("00000001 exit status for
aicrom_init"), and the utility goes on. So the DS15 row builds nothing
there.

**show config, open items (L3):**

- "Intlv Mode" prints a large number. `showmem` (0x90f60 in the installed
  console) prints 1-way when Cchip CSC<51> is set, 2-way when arrays 0 and 2
  have the same size, and an uninitialised register otherwise; with one
  1024 MB array and CSC<51> clear it is the last. Which is right for a DS15
  is not known, and CSC is the chipset's, shared with the ES45 and DS25.
  The owner's guide shows one 1024 MB array as "1-Way" (example 2-7) and
  arrays 0 and 2 of 1024 MB as "2-Way" (example 2-5): a one-array DS15 has
  CSC<51> set, or the DIMM model should place a DS15's memory in arrays 0
  and 2. Not changed: CSC and the DIMM model are shared with the ES45 and
  DS25.
- The TIG revision: the DS15 console prints TIG offset 0 as "<7:4>.<3:0>"
  (the Titan model's 0x06 printed "0.6"); `CDs15Tig` answers 0x19, the
  guide's "TIG Rev 1.9".
- "SROM Extended", "SROM Fail Safe", "RMC Runtime", "RMC Booter" print
  empty: the DS15 keeps these versions somewhere in the DPR the model does
  not fill.

Other unclaimed accesses at power-up: PA-chip port CSR offset 0x550 of both
ports written with 0 by the PALcode (`ra=0x130d4`), TIG 0x4c0 (`clr_temp_warn`
in the ES40's naming) written with 1, and TIG 0x4000000/0x4000040 (a TIG-bus
device at 0x801.4000.0000) read once each.

# AlphaServer DS10 work packet

The second machine after the DS20E pilot, and the first one that did not
simply work: its console loaded, ran, and then walked into its own
assertion. The cause was a piece of hardware nobody had modelled -- the
board's I2C bus controller -- and with it in place the console reaches its
prompt and names the machine correctly.

**Branch**: `platform/ds10` · **Config**: `platform = "ds10";`
· **Status**: L2 (console prompt, `show config` / `show memory` /
`show device` answer; L3 needs a reference listing)

## The machine

| | |
| --- | --- |
| Family, code name | Tsunami family; Linux calls this board "Webbrick" and carries its own interrupt table for it |
| CPU | one, EV6 or EV67 (assumed, from hardware listings). The EV68CB row is used for now, as on the DS20E |
| Chipset | Tsunami/Typhoon 21272, one PCI bus (Linux: "DS10 has only 1 hose"); the console lists Cchip, Dchip, one Pchip, TIG and an arbiter |
| Memory | up to 2 GB (assumed) |
| PCI | two on-board network controllers at devices 9 and 11, four slots at devices 14 to 17, ISA bridge at 7 (known: Linux `webbrick_map_irq`) |
| Board hardware | a PCF8584 I2C bus controller at PCI 0 memory `0xffff0000` (**known**, see Findings), carrying the remote management controller's non-volatile memory and three or four other parts; the diagnostic byte PALcode writes goes to PCI memory `0xffff0000` too -- the same address the controller answers at, which is what put an earlier note in this packet on the wrong track |

## Firmware

- Image: `roms/alpha-firmware-v7.3/DS10/DS10SRM.ROM` (Alpha firmware CD
  V7.3), 767 KB, standard Alpha ROM header, loads at 0x900000. The same
  loader as the DS20E reads it. Console V7.3-1, built Feb 27 2007, with
  OpenVMS PALcode V1.98-83 and Tru64 PALcode V1.92-73.
- Also present: `PC264NT.ROM` (AlphaBIOS), `DS10_V7_3.EXE` (update bundle).

## Findings

**It loads and runs, and then asserts.** The board row plus the ROM-header
loader get the DS10 console executing: it greets the serial port, sizes
memory ("64 Meg of system memory") and then reports `SYSFAULT CPU0 - pc =
001cd0a8`, dumps registers and call frames, and halts.

**What the fault actually is.** The frame dump names three routines, and the
console's own symbol table names the rest:

```
build_hwrpb+0x22c -> build_dsrdb+0x94 -> fread+0x80 -> sysfault
```

`build_dsrdb` builds the Dynamic System Recognition database -- the record
that says which machine of a family this one is. It does:

```
fopen("iic_rcm_nvram0", "srb")   ; the management controller's serial ROM
fseek(fp, 17, SEEK_SET)
fread(&byte, 1, 1, fp)           ; one byte, at offset 17
```

and it never looks at what `fopen` returned. `fread`'s first act is
`beq a3, <assert>`: a null file pointer is an assertion failure, which calls
`sysfault` with code 0x64. That matches the register dump exactly (a0 =
0x64, a3 = 0, a1 = a2 = 1, and t6 = 0xfe00, `fread`'s own size limit). The
reported `pc = 001cd0a8` is the return address inside the fault reporter,
not a bad instruction.

The failure is silent by design: `fopen`'s error path checks the mode string
for `g` or `s` and prints nothing when it finds either, and this console
opens with `"srb"`. So the machine says nothing at all until the assertion
fires.

**Why the open failed: the board's I2C bus controller was missing.** The
console reaches its serial ROMs through a **PCF8584 I2C bus controller at
PCI 0 memory `0xffff0000`** -- S0, the data shift register, at `+0`, and S1,
control on write and status on read, at `+1`. Its own `iic_write_csr` and
`iic_read_csr` build exactly that address, and `iic_reset` writes the
part's textbook initialisation sequence into it: S1 = 0x80, S1 = 0x00,
S0 = own address 0x5b, S1 = 0x20, S0 = clock 0x15, S1 = 0xc0.

Nothing answered there, so reads returned 0, so bit 0 of the status --
BB, the bus-free bit -- never set. `iic_busb` waits for it a hundred
thousand times before giving up, `iic_init` fails for every part in the
console's I2C database, no inode is created for `iic_rcm_nvram0`, and the
open fails. Fifty-six of those cycles go by in a boot, one per entry in
that database, which is what the repeated register writes in the
unknown-access trace were.

Two smaller things fell out of the same work:

- The reads were invisible in the trace because a range check in
  `CSystem::ReadMem` swallows unclaimed PCI memory from `0x800000c0000`
  right up to `0x801000e0000` as "unused PCI ROM BIOS space", returning 0
  without a word. `0xffff0000` is inside it. The writes were reported;
  the reads were not. That asymmetry cost time and is worth fixing.
- `Eeprom24C02`, the I2C part the SPD model uses, released its acknowledge
  one clock early: it moved state on the falling edge that ends the eighth
  clock, so a master that samples SDA during the ninth clock -- which is
  where the acknowledge belongs -- saw nothing. Nothing had ever exercised
  it (neither the ES40's console nor the DS20E's touches an I2C bus at
  all), so the bug had never shown. It now holds the acknowledge until the
  ninth clock has been taken.

**What the console looks for on that bus.** With the controller in place it
addresses 0x38, 0x39, 0x4f, 0x51 and 0x60 to 0x67, and names the last eight
itself: they are `iic_rcm_nvram0` to `iic_rcm_nvram7`, the remote
management controller's non-volatile memory, with `iic_rcm_nvram0` at 0x60.
(The console printed `iic_rcm_nvram0 command timeout!` the moment 0x60
started acknowledging, which is how that mapping was confirmed.) The other
four are `iic_system0`, `iic_system1`, `iic_rcm_temp` and `iic_smb0` in
some order; neither the parts nor their contents are known, so they are
left unanswered. The console complains "IIC bus Status (01) error" three
times and carries on.

**The serial ROMs are erased parts, and that is a choice.** The board row
hangs eight read-only serial ROMs at 0x60 to 0x67, every byte 0xff -- what
an unprogrammed part reads as. What a real DS10's management controller
holds we do not know and did not invent. The console's own code makes this
harmless: `build_dsrdb` masks the byte at offset 17 to four bits and treats
any value of 6 or more as no code, so an erased part reads as "nothing
recorded" and the console falls to the first entry of its table. That entry
is `AlphaServer DS10`, which is the right answer for this machine -- but it
is the right answer by luck, not by evidence. A machine whose management
controller records one of codes 1 to 5 would name itself differently; the
DS20E packet found the same mechanism there, with a table of six DS20 and
DS20E variants.

**The console now reaches its prompt (L2).**

```
$ PLATFORM=ds10 ROM=roms/alpha-firmware-v7.3/DS10/DS10SRM.ROM \
    CMDS="show config|show memory|show device" PORT=21613 \
    test/tools/srm_probe.sh build/alphabox ds10 300
  status=prompt
                          AlphaServer DS10 800 MHz
  SRM Console:  V7.3-1
  PALcode:      OpenVMS PALcode V1.98-83, Tru64 UNIX PALcode V1.92-73
  Processors
  CPU 0         Alpha EV68CB pass 4.0 800 MHz
  Core Logic
  Cchip         DECchip 21272-CA Rev 9
  Dchip         DECchip 21272-DA Rev 2
  Pchip 0       DECchip 21272-EA Rev 2
  TIG           Rev 7.30
```

Its prompt is a bare `>>>`, not the ES40's `P00>>>`; `srm_console.py` now
accepts a `>>>` that ends a line, which is why the probe reports
`status=prompt` at all.

**What it still complains about, and what each one is:**

- `SROM Revision:` prints rubbish and `Bcache is disabled` -- the same
  unfilled per-processor SROM records as on the DS20E, whose packet traced
  them to an empty list at a known address.
- `Vector allocation failed for hose 0, bus 0, slot 15, pin 1, irq 39` /
  `Vector 00b7 already allocated`. The test configuration puts the ALi
  M1543C's IDE function at PCI device 15, which on this board is one of the
  four real add-in slots (14 to 17), and its interrupt collides. The
  M1543C's functions need a placement of their own on this machine; the
  board's `slot_refusal` does not refuse it today because the standard
  configuration would then not start at all.
- `ERROR: ISA table corrupt! / Initializing table to defaults` on a first
  boot with empty non-volatile storage, and `*** system serial number not
  set`, both expected on a machine that has never been configured.
- Three unmodelled TIG registers read (`0x28000000`, `0x38000140`,
  `0x380001c0`) and one written (`0x38000100`), the same set the DS20E
  reads and writes, where feeding different values changed nothing.

**Reading this console's own names.** Unlike the DS20E's image, `DS10SRM.ROM`
carries a symbol table: pairs of 32-bit (procedure descriptor, name string)
words, 2832 of them, at `0x167d90` to `0x16d610` in the decompressed image
(`rom.decompressed`, whose image starts 16 bytes in at address 0; `strings
-t x` offsets are 0x10 high for the same reason). A procedure descriptor's
entry point is the quadword at `+8`. That turns every trace address into a
name, which is what made this fault readable.

To see which routines actually ran, `ALPHABOX_TRACE_CALLS=1` reports each
subroutine call the first time a given site reaches a given routine --
the console's own call graph, about 800 lines for a boot that faults and
2600 for one that reaches the prompt. It is what showed that `iic_open` was
never reached, and therefore that the file was never found rather than the
transfer failing. Interpreter lanes only: compiled blocks do not pass
through the interpreter's call macros.

## Rules

As in [TEMPLATE.md](TEMPLATE.md): firmware from the user's own media, no
behaviour change for other machines, no register given a convenient value
to get past a problem, and report the level actually reached.

The one value chosen rather than known is the content of the serial ROMs at
0x60 to 0x67: erased, 0xff throughout, marked as such here and in
`ds10_i2c_devices` in `src/platforms/Platforms.cpp`.

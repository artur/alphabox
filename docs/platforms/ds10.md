# AlphaServer DS10 work packet

The second machine after the DS20E pilot, and the first one that does not
simply work: its console loads and runs but stops early in its own file and
flash layer. What is known is below; the blocker is item 1.

**Branch**: `platform/ds10` · **Config**: `platform = "ds10";`
· **Status**: L1 (firmware loads and executes; no prompt)

## The machine

| | |
| --- | --- |
| Family, code name | Tsunami family; Linux calls this board "Webbrick" and carries its own interrupt table for it |
| CPU | one, EV6 or EV67 (assumed, from hardware listings). The EV68CB row is used for now, as on the DS20E |
| Chipset | Tsunami/Typhoon 21272, one PCI bus (Linux: "DS10 has only 1 hose") |
| Memory | up to 2 GB (assumed) |
| PCI | two on-board network controllers at devices 9 and 11, four slots at devices 14 to 17, ISA bridge at 7 (known: Linux `webbrick_map_irq`) |
| Board hardware | unknown beyond the above; the diagnostic byte PALcode writes goes to PCI memory `0xffff0000`, where the DS20E uses `0xfff80000` |

## Firmware

- Image: `roms/alpha-firmware-v7.3/DS10/DS10SRM.ROM` (Alpha firmware CD
  V7.3), 767 KB, standard Alpha ROM header, loads at 0x900000. The same
  loader as the DS20E reads it.
- Also present: `PC264NT.ROM` (AlphaBIOS), `DS10_V7_3.EXE` (update bundle).

## Sources

- Linux `arch/alpha/kernel/sys_dp264.c`: `webbrick_map_irq`, `webbrick_mv`.
- The DS20E packet ([ds20e.md](ds20e.md)): same chipset, same firmware
  family, and the techniques that worked there.

## Findings

**It loads and runs.** The board row plus the ROM-header loader get the
DS10 console executing: it greets the serial port, sizes memory ("64 Meg of
system memory") and then reports `SYSFAULT CPU0 - pc = 001cd0a8`, dumps
registers and call frames, and halts. The frame dump names the routine it
faulted in: `fread`, the console's own file read. The address it reports is
where its fault reporter was called from, not a bad instruction -- the
console walked into this deliberately, the way an assertion does.

**What it is not.** Each of these was tested and changed nothing:

- *The flash part.* With `ALPHABOX_TRACE_FLASH=1` the console runs the
  AMD-style identify sequence (`aa`, `55`, `90`), reads manufacturer,
  device and protection, and repeats the whole thing about sixty times
  before giving up. Offering it other identities (AMD 4 MB, 1 MB, 512 KB,
  an Intel part, another maker's 2 MB) produces exactly the same fault.
- *The flash contents.* Seeding the flash with this machine's own console
  image, as a real machine's flash carries, changes nothing.
- *Missing on-board devices.* Adding the two network controllers at devices
  9 and 11 changes nothing.
- *The processor count and the interrupt table* are not involved: the fault
  happens before any of it matters.

For comparison, the DS20E console performs the same identify sequence and
then uses the flash heavily (about half a million accesses in a boot,
against this one's six hundred).

**Where to look next.** Disassemble the console's `fread` and its flash or
file-system initialisation in the decompressed image (the emulator writes
it out as `rom.decompressed`, the image starts 16 bytes in at address 0,
and `lab/alphadis.py` disassembles it). The DS20E packet's "how to read
this firmware" section describes the path from a traced access to the
calling code. The question to answer is what this console reads before it
decides to fault -- most likely a file or a flash structure it expects and
our blank flash does not provide in the form it wants.

## Rules

As in [TEMPLATE.md](TEMPLATE.md): firmware from the user's own media, no
behaviour change for other machines, no register given a convenient value
to get past a problem, and report the level actually reached.

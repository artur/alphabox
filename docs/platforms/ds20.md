## Findings

**How the console knows which machine it is on (2026-10-20).** One image
serves the AlphaPC 264DP, the DS20 and the DS20E. The routine at 0x7fd80
of the decompressed V7.3-1 computes the HWRPB's system variation from
which I2C parts its driver found:

- no `iic_rcm_temp` (the RCM's thermometer, bus address 0x4f): 0x405,
  member 1, the AlphaPC 264DP;
- `iic_rcm_temp` but no `iic_8574_ocp` (the operator panel's PCF8574,
  0x27): 0x1805, member 6, the AlphaServer DS20;
- both: 0x2005, member 8, the DS20E.

The only reader of the member number found in the console is the routine
at 0x7fa78, which builds the DSR block (a search of the disassembly for
the field's shift and the member values finds no other).

The names and bus addresses are the console's own: a table at 0x15d618
with a row per part (name, kind, size, 8-bit address): `iic_cont` (the
PCF8584 itself, 0x5b), `iic_ocp0`/`iic_ocp1` (0x20, 0x21),
`iic_8574_ocp` (0x27), `iic_smb0` (0x51), `iic_cpu0`/`iic_cpu1` (0x52,
0x56), `iic_system0`/`iic_system1` (0x38, 0x39), `iic_rcm_temp` (0x4f)
and `iic_rcm_nvram0` to `7` (0x60 to 0x67). The DS20E row hangs parts at
0x27, 0x4f and 0x60 to 0x67; the DS20 row is the same without 0x27. The
I2C trace shows the result: the console's writes to 0x27 go unanswered
and its reads elsewhere are as on the DS20E (`lab/t1/ds20-i2c-seq.txt`
against `lab/t1/ds20e-i2c-seq.txt`).

What else a real DS20 has on that bus (the other OCP parts, the FRU
serial ROMs) is not known, and the console needs none of it to reach its
prompt and boot.

**The machine table (2026-10-20).** Entries of 44 bytes at 0x156850: a
system marketing model number (SMM), a nine-entry LURT (the licence-unit
table of the HWRPB's DSR block) and a pointer to the name. The DS20E packet read the SMMs one entry
off; corrected, they are:

| Entries | SMM | LURT[0] | Name |
| --- | --- | --- | --- |
| 0 | 0x72e | 15 | AlphaPC 264DP |
| 1, 2 | 0x72e, 0x780 | 25, 75 | AlphaServer DS20 |
| 3-8 | 0x730, 0x781, 0x793, 0x794, 0x7be, 0x7bf | 25, 75 alternating | COMPAQ AlphaServer DS20E |
| 9-14 | 0x795, 0x796, 0x797, 0x798, 0x7ac, 0x7ad | 20, 70 alternating | COMPAQ AlphaStation DS20E |

The DSR the console builds on the `ds20e` row (memory at the prompt)
confirms the pairing: SMM 0x795, LURT 20, "COMPAQ AlphaStation DS20E 800
MHz".

The routine at 0x7fa78 picks the entry:

- member 1: entry 0;
- member 6 (DS20): entry 1, or 2 when the processor's SROM data records
  another processor;
- member 8 (DS20E): by the processor type the console stores at 0x4084
  (11 EV67, 13 EV68AL, anything else the first pair: EV6, and the
  EV68CB row's 12), by bit 0 of byte 17 of `iic_rcm_nvram0` (1 an
  AlphaStation, 0 an AlphaServer), and by the same SROM test.

The SROM data (0x4200 + 0x600 per processor, a signature `0xdec` at
+0x430 and a processor mask at +0x438) is not modelled, as the DS20E
packet records, so the second entry of a pair is never chosen: a
two-processor DS20 is named with SMM 0x72e, as a one-processor one.
OpenVMS reads the SMM as `HW_MODEL` (below).

**The console on the `ds20` row (2026-10-20, L2 and L4).** It reaches
`P00>>>` first time and names itself "AlphaServer DS20 800 MHz"
(`lab/t1/evidence/probe-t1-ds20-first`). Its log has the DS20E's
messages, with one `IIC bus Status (01) error` fewer (four against five;
on its bus the console no longer reads `iic_rcm_nvram0` byte 17, and its
accesses to 0x27 go unanswered). Which access the missing message
belonged to was not traced. The rest is the DS20E's: the ISA table
initialised on a fresh NVRAM, the IDE's shared vector, `file open failed
for iic_cpu0`, the thermometer's 255 degrees, the I2C errors from parts
no row provides. With two processors both are listed (`Active CPUs: 00
01`); a 53C875 at device 7 lists
`dka0` and `dka500`; a DE600 at device 8 boots over BOOTP and TFTP from
`net_peer.py` to the image's HALT (`probe-t1-ds20-2cpu-scsi`,
`probe-t1-ds20-net`).

### OpenVMS 8.4 (2026-10-20, L5)

Driven by `lab/platforms/tsu/tsu_srm.sh` with `lab/t1/tsuboot.py`, device
layout `lab/t1/ds20-ide.cfg` (the DS20E's: ISA bridge `pci0.5`, IDE
`pci0.6`, the installed disk `dqa0`, the CD `dqa1`), 1 GB. Run
directories `lab/runs/tsu-t1-ds20-*`; transcripts copied to
`lab/t1/evidence/`. Seconds from `boot`:

| Run | Lane, CPUs | Result |
| --- | --- | --- |
| `tsu-t1-ds20-cd` | JIT, 1 | `boot dqa1`: banner 20, date prompt 59, installation menu 95 |
| `tsu-t1-ds20-disk-1cpu` | JIT, 1 | `boot dqa0`: startup done 21, SYSTEM logged in 38 |
| `tsu-t1-ds20-disk-2cpu` | JIT, 2 | `%SMP-I-CPUTRN, CPU #1 has joined the active set`, logged in 36, `SHOW CPU` active 0,1 |
| `tsu-t1-ds20-disk-2cpu-int` | interpreter, 2 | the same, logged in 47 |
| `tsu-t1-ds20-nic` | JIT, 1 | three DE500s receive (below) |

OpenVMS calls the machine `AlphaServer DS20 833 MHz` (`HW_NAME`), with
`HW_MODEL` 1838 (0x72e, the console's SMM) and SYSTYPE 34, on one and on
two processors. After login each disk run copies `SYS$BASE_IMAGE.EXE`
with BACKUP and compares it (`DIFFERENCES`: 0 sections).

**Interrupts, checked with a guest driver.** Three DE500s (dec21143, UDP
backend) at hose 0 device 7, hose 0 device 9 and hose 1 device 8, with
`MC LANCP SET DEVICE EWx0/MOPDLL=ENABLE` and `lab/t1/frame_tx10.py`
sending a broadcast frame to each every 0.5 s. `Packets received` after
about 45 s:

| Place | Line the console assigned | Received |
| --- | --- | --- |
| hose 0 device 7 (EWB0) | 0x1f | 90 |
| hose 0 device 9 (EWC0) | 0x17 | 88 |
| hose 1 device 8 (EWA0) | 0x2b | 90 |

The lines are what the console wrote into each device's configuration
space (`pci-interrupts.txt` in the run's evidence), the same as on the
DS20E.

### Nothing else changed (2026-10-20, L6)

The DS20E's board code now builds its I2C parts through the function the
DS20 shares. Its console log and its whole I2C conversation are
byte-for-byte what they were before the change (interpreter,
`lab/t1/ds20e-i2c-seq.txt` against `ds20e-i2c-seq-after.txt`), and it
reaches `P00>>>` as "COMPAQ AlphaStation DS20E 800 MHz" on the JIT lane
too. The ES40's `srm_run.sh` is diff clean on the interpreter and JIT
lanes (`lab/t1/regress-*.txt`). Nothing in the processor or the JIT
changed, so the JIT_VERIFY lane was not run.

## Rules

- Firmware images are copied from media the user owns, never downloaded.
- Existing machines must not change behaviour: the ES40 console-log check
  stays clean and the JIT cross-check stays at 0 mismatches (L6).
- An unknown register access is traced and reported, never given a
  convenient value to make the firmware proceed. A value chosen to satisfy
  the firmware is marked as such, in the code and in **Findings**.
- Report the highest acceptance level actually reached, with the command
  output that shows it.
